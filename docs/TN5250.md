# TN5250E in QS/400

Phase 8 gives QS/400 a real 5250 display interface: a TN5250E server
(`QTVTELNET`), virtual display devices, the 5250 data stream, and a
screen model every display in the system writes through. This
document is the reference for the crate `ui/tn5250`, the server role
of `qsjob` (`work/qsjob/src/work/telnet.rs`), the device objects, and
the scripted display `tools/tn5250-driver` that captures and compares
screens on QS/400 and on the oracle systems.

## Oracles and what was observed

Only pub400.com (IBM i 7.5) exposes telnet; the primary oracle
(V7R1M0) offers only its host-server ports, so every observation of
the wire below is pub400's. The driver's `--trace --hex` mode records
them; nothing here is from documentation alone.

The server opens with `DO NEW-ENVIRON` and `DO TERMINAL-TYPE`. After
the client's two `WILL`s it sends the environment `SEND` and the
terminal type `SEND`, then `DO EOR`, `WILL EOR`, `DO BINARY`, `WILL
BINARY`, in that order, each answered by the client. Exact bytes of
pub400's `SEND`:

```
IAC SB NEW-ENVIRON SEND USERVAR "IBMRSEED" <8 seed bytes> VAR USERVAR IAC SE
```

The seed follows the name directly: it is part of the `USERVAR`'s
name bytes, not a `VALUE` (RFC 4777 says so; the four special bytes
inside it are escaped with `ESC`). QS/400's server sends the same
shape; its client reads either shape.

The client's `IS` carries `VAR USER`, `USERVAR IBMRSEED` (the client's
seed), `USERVAR IBMSUBSPW` (the substitute), `USERVAR DEVNAME`,
`KBDTYPE`, `CODEPAGE`, `CHARSET`. pub400 accepted the SHA-1 substitute
and went straight to the user's initial menu: that verifies
`pwdsub::sha_password` against a real system. The DES substitute
cannot be verified from this machine (no level 0/1 system with telnet
reachable); it follows JTOpen's `generateToken` and
`generatePasswordSubstitute` step for step.

pub400 sends no start-up response record when no `DEVNAME` was asked
for. QS/400 sends one (`I902` + the device name, EBCDIC, after a
ten-byte header with opcode 0) only when the client asked for a
device; the exact bytes of a real one are still unverified
(`BLOCKED(phase8)`: an ACS packet trace needs a reachable telnet on
the primary oracle).

After sign-on pub400 sends a Query (`WSF D9 70`); our terminal answers
with the query reply in `ds::wdsf::query_reply`, claiming a 3179-2 or
3477-FC, color, and GUI constructs only when asked (`--gui`); without
GUI the host draws windows with characters, which is what goldens
want.

## Records

Every 5250 record is a General Data Stream record:

| Bytes | Content |
|---|---|
| 0-1 | record length, the whole record including this field |
| 2-3 | `0x12A0` |
| 4-5 | reserved, zero |
| 6 | variable header length, 4 |
| 7-8 | flags: `0x8000` ERR, `0x4000` ATN, `0x0400` SRQ, `0x0200` TRQ, `0x0100` HLP |
| 9 | operation code |
| 10- | data |

followed on the wire by `IAC EOR`; `IAC` inside data is doubled. The
length field counting the whole record was confirmed against pub400
(a 791-byte sign-on record carried `03 17`).

Operation codes: 0 no-op, 1 invite, 2 output only, 3 put/get, 4 save
screen, 5 restore screen, 6 read immediate, 8 read screen, 10 cancel
invite, 11 message light on, 12 message light off.

## The data stream

Commands follow `ESC` (`0x04`):

| Byte | Command | Parameters |
|---|---|---|
| `40` | Clear Unit | |
| `20` | Clear Unit Alternate | one byte, `00` for 27×132 |
| `50` | Clear Format Table | |
| `11` | Write To Display | CC1, CC2, orders |
| `21` | Write Error Code | orders written on the error line |
| `22` | Write Error Code To Window | two bytes, orders |
| `42` | Read Input Fields | CC1, CC2 |
| `52` | Read MDT Fields | CC1, CC2 |
| `82` | Read MDT Fields Alternate | CC1, CC2 |
| `62`,`64`,`66`,`68` | Read Screen variants | |
| `72`, `83` | Read Immediate, alternate | |
| `02`, `03` | Save Screen, Save Partial Screen | the latter three bytes |
| `12`, `13` | Restore Screen, Restore Partial Screen | the saved data follows |
| `23` | Roll | direction and lines, top, bottom |
| `F3` | Write Structured Field | length, class `D9`, type, body |
| `16` | Copy To Printer | one byte |

Orders inside Write To Display, as pub400 sends them:

| Byte | Order | Parameters |
|---|---|---|
| `01` | Start of Header | length (up to 7), flags, reserved, resequence, error row, three key-switch bytes |
| `02` | Repeat to Address | row, column, byte |
| `03` | Erase to Address | row, column, length, attribute types |
| `10` | Transparent Data | two length bytes, data |
| `11` | Set Buffer Address | row, column |
| `12` | Write Extended Attribute | type, value |
| `13` | Insert Cursor | row, column |
| `14` | Move Cursor | row, column |
| `1D` | Start of Field | FFW, FCWs, attribute, two length bytes |

(The first trace corrected two guesses: Start of Header is `0x01` and
Transparent Data `0x10`.) Bytes `0x20` to `0x3F` in data are
attributes, `0x00` null, `0x1C` dup, `0x1E` field mark; everything
else is EBCDIC in the device's code page (CP037 here).

CC1's high three bits lock the keyboard and reset or null fields
(`ds::cc1`); CC2 bits are blink (`0x40`, `0x20`), unlock (`0x08`),
alarm (`0x04`), message light (`0x02`, `0x01`). pub400's sign-on
Write To Display carries CC2 `0x18`.

The Field Format Word (`ds::field::Ffw`): bypass, dup, MDT, the shift
type (alpha shift, alpha only, numeric shift, numeric only, katakana,
digits only, I/O, signed numeric), auto enter, field exit required,
monocase, mandatory entry, right adjust zero or blank, mandatory fill.
Field Control Words are kept as read; cursor progression (`0x80nn`),
continued entry (`0x86`), transparency (`0x88`) and highlighted entry
(`0xB4`) are the ones the runtime will act on.

Attributes `0x20`–`0x3F`: green, white, red, turquoise and yellow
(column separators), pink and blue; each with reverse image,
underline and (red) blink; `x7`/`xF` nondisplay.

Attention identifiers: Enter `F1`, Help `F3`, Roll Down `F4`, Roll Up
`F5`, Print `F6`, Record Backspace `F8`, Clear `BD`, Auto Enter `3F`,
`F1`–`F12` `31`–`3C`, `F13`–`F24` `B1`–`BC`, Query reply `88`. System
Request, Attention and Test Request travel as header flags with no
AID.

## The terminal (`term`)

The client side: a cell grid (24×80 or 27×132), the format table, the
cursor, the keyboard lock (`X SYSTEM`) and the error state (`X II`).
It applies every command above, answers Read Immediate, Read Screen,
Save Screen (with a `Restore Screen` command followed by a Clear Unit
and one Write To Display that rebuilds the screen, fields as Start of
Field orders with their MDT bits), Cancel Invite and the Query. The
keyboard runs on the station: typing with shift and monocase checks,
insert mode, auto advance and auto enter, Field Exit with right
adjustment and signed numeric sign positions, Field+/Field−, Erase
EOF, Erase Input, Dup, Home, the cursor keys. Operator errors
(`term::keys::err`) inhibit the keyboard until Reset. An attention key
sends the cursor, the AID and the fields the outstanding read asks
for: modified fields with trailing nulls stripped for Read MDT
Fields, every field with nulls as blanks for Read Input Fields.
Without an Insert Cursor order the cursor rests in the first input
field when the keyboard opens (pub400's sign-on sends none).

`text_rows` is the character grid (attributes and nulls blank,
nondisplay runs blank, dup as `*`); `attr_rows` the attribute in
force at every cell, `#` where an attribute byte sits. The driver's
goldens are these two grids after masking.

## The screen model (`screen`)

The host side: what a job wants shown, as cells and fields, rendered
as the stream that brings the client there. The first render clears
the unit and sends the whole screen behind a Start of Header; later
renders send only the rows that differ from what the client was last
sent, with CC1 `0x40` so stale MDT bits are reset. Text is placed with
its leading attribute in the cell before and a return to green after
(a field at column 1 has its attribute at the end of the previous
row, exactly as IBM lays its screens out). Nulls at the end of a row
go as Repeat to Address. A read opens the keyboard with Read MDT
Fields (opcode put/get); without a read the record is output only.
`accept` takes the inbound record, updates the fields it names and
returns the AID. `invalidate` forgets the client's state, for a
reconnected or replaced display.

Panels of earlier phases (`wm::ctl::Panel`) render through
`work/qsjob/src/display/mod.rs`: text attribute codes map to green,
white, blue and red; input fields are underlined green (nondisplay
for passwords, reverse image when in error); the message goes on the
last row in white, replacing what was there, with an alarm when it is
an error.

## Devices and the server

`QTVTELNET` (`QTCP` in `QSYSWRK`) is a `qsjob` role started by
`STRTCPSVR SERVER(*TELNET)`, which `QSTRUP` runs after the subsystems.
It listens on port 23 (`CHGTELNA` keeps its attributes in the data
area `QUSRSYS/QTVTELNA`; `PORT(n)` there moves it, which the harness
needs). Each connection is a thread registered as a `QTVDEVICE` job:

1. negotiation (`telnet::server::Server`);
2. a display through the storage service (`device_allocate`): the
   device the client named, created under `QAUTOCFG` when missing,
   else a free virtual display, else a new `QPADEVnnnn` (hexadecimal
   digits like IBM's) within `QAUTOVRT`, with the controller
   `QPACTL01` (`*CTLD`, `*VWS`) made on first use; beyond the limit the
   session is refused with `8940` and `QSYSOPR` gets `CPF8955`;
3. the start-up response when a device was named;
4. RFC 4777 auto-signon when `USER`, `IBMRSEED` and `IBMSUBSPW` came:
   the service compares the substitute with the one it computes from
   the stored token (`sign_on_substitute`);
5. else the sign-on display (`wm::panels::sign_on`, the layout of
   `QDSIGNON`), checked by the same `sign_on` the console uses;
6. the interactive job: routed by the workstation entries of the
   active subsystems (a name entry for the device, else a type entry
   `*ALL`), spawned by the session with `Start.device` set, so the job
   opens its display socket at `/run/qs400/dev/<DEVICE>` (`wm::dev`);
   from then on the session only moves records between the socket and
   the connection;
7. when the job ends (sign-off) the sign-on display returns; when the
   connection drops, `QDEVRCYACN` decides: `*ENDJOB` and
   `*ENDJOBNOLIST` end the job, the others keep it disconnected until
   the same user signs on again (any device; the job's screen is
   resent whole) or `QDSCJOBITV` minutes pass. `DSCJOB` does the
   same on purpose.

Device status (`WRKCFGSTS CFGTYPE(*DEV)`, `DSPDEVD`): varied off,
varied on, sign-on display, active, recovery pending. `CRTDEVDSP`,
`CHGDEVD`, `DLTDEVD`, `VRYCFG`, `WRKCFGSTS CFGTYPE(*CTL)` manage the
objects.

Password tokens: setting a password also stores its RFC 4777 tokens
(the DES form of a short password, the SHA-1 form of the password as
the level signs on with) in the profile beside the Argon2id hashes
(`PwdForm::DesToken`, `PwdForm::ShaToken`), so a substitute can be
checked without the password. The tokens never leave the store.

## The harness

The QEMU launch gains a user-mode network device with the guest's
port 23 forwarded to a free host port (`Launch.telnet_port`); `slic`
gives the first Ethernet link `10.0.2.15/24` (or `qs400.ip=` from the
command line) with rtnetlink. Step 51 connects with the driver's
library, signs on, reaches MAIN and Command Entry, runs `WRKACTJOB`
and sees its own `QPADEV` job and the server, signs off, and checks
`WRKCFGSTS` from the service console. `conformance --only 51` runs
the boot and that step alone.

## The driver

`cargo run -p tn5250-driver -- run --target qs400|oracle|pub400
[--host H:P] [--auto-signon [--encoding des|sha]] [--model m3179|m3477]
[--gui] [--trace [--hex]] [--golden DIR [--update]] script.tn...`
runs keystroke scripts (`script.rs` documents the steps) over one
session; `snap NAME` captures or compares a golden (`NAME.txt`,
`NAME.attr`, and `INDEX.toml` with the source, release, date, script
and width). Masks keep every screen's width: dates, times, the system
name and the user by default; job numbers, device names, serial
numbers on request (`snap NAME +jobnum`). `ftp --target ... ls|get|
put|quote` uses the oracle's FTP server. Credentials come from the
environment or `tools/conformance/oracle/.env`, never from anywhere
else; traces hide nondisplay fields.
